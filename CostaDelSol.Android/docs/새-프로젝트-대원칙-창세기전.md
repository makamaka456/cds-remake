## 1. 목표

- 윈도우11용 창세기전 리메이크를 **개인용 안드로이드 APK** 로 만든다(폰 · 레트로이드 같은 휴대 게임기).
- 원본 게임 자료는 APK 에 넣지 않는다(§4). 결과물은 개인 사용용이다.

## 2. 저장소 · 브랜치 원칙

1. **작업은 포크 하나(`makamaka456/the-war-of-genesis-clicker`)에서만.** iOS 저장소는 포크하지 않는다.
2. **원본 코드는 고치지 않고 그대로 링크한다** — 안드로이드 프로젝트(예: `WarOfGenesis.Android/`)의 csproj 가
   `<Compile Include="..\WarOfGenesis.Assets\X.cs" Link="Shared\..." />` 로 원본 파일을 끌어 쓴다. 안드로이드에 없는 것만 얇게 흉내 낸다.
   - 꼭 고쳐야 하면 `#if ANDROID` 로 **작게** 고치고, 고친 파일 목록을 인계 노트에 적는다(병합 때 살핀다).
   - 원본의 큰 파일을 통째로 갈라 만들어야 하면(대항해시대의 `WorldMapWindow`처럼) 갈라 만든 파일 목록을 두고 **3-way 병합 스크립트**로 원본 변경을 따라간다(참고: cds-remake `CostaDelSol.Android/devtools/merge-forks.sh`).
3. **원본 업데이트를 계속 받는다**: `git remote add upstream https://github.com/Kyeongrok/the-war-of-genesis-clicker.git` → `git fetch upstream --tags` → 원본 판 태그(`v1.0.xx`)를 병합.
4. **브랜치**: 클라우드 세션은 세션마다 푸시할 브랜치가 정해진다(예: `ccr-xxxx`). 사용자가 정한 브랜치 이름만 쓰고, 다른 브랜치로 푸시하지 않는다. PR 은 사용자가 말할 때만.
5. **태그 충돌 주의(대항해시대에서 겪음)**: 원작자 워크플로가 `v*` 태그에 PC 판을 굽는다. 안드로이드 릴리즈 태그는 반드시 **`android-v0.x.y`** 로 하고, 릴리즈 안내 때마다 사용자에게 `android-` 를 꼭 붙이라고 말한다.
6. 시험이 만든 그림 · 결과 글이 저장소 맨 위에 쌓이지 않게 한다(시험기는 scratchpad 안에서 돌리고, `.gitignore` 에 `/*.png`, `/qa-*.txt`).

## 3. iOS 저장소(sonicusers/twgios) 활용 원칙

- 코드를 통째로 옮기지 않는다(Swift → 안드로이드 직접 사용 불가).
- "설치된 리메이크 파일을 어떻게 찾고 · 불러오고 · 실행하는지" 방식만 분석해 안드로이드로 다시 구현한다.
- 코드를 조금이라도 가져올 때는 라이선스를 확인하고 출처를 적는다. 라이선스가 없거나 불명확하면 **방식만** 참고한다.
- 참고: iOS 앱 방식("설치된 리메이크를 불러와 실행")은 계정 스킬 **`android-runtime-patch-port`**(릴리즈된 dll 을 폰에서 고쳐 돌리는 런처 방식)와 같은 계열이다. 아래 §5-3 에서 두 길을 비교해 사용자에게 고르게 한다.

## 4. 원본 게임 자료 원칙

- 원본 게임 자료는 **APK 에도, 저장소에도, GitHub 릴리즈에도 넣지 않는다**(공개 저장소의 릴리즈는 누구나 받을 수 있다 = 배포다).
- APK 설치 뒤 사용자가 폰의 폴더(또는 zip)에 원본 자료를 넣고, 앱이 그 자리를 `OriginalGame.Use(...)` 처럼 원본 코드의 길로 건넨다.
- 필요한 파일 목록은 **코드 분석으로 확정**한다(`OriginalGame.IsValid`, `GameFiles.FromGameRoot`, `Part1Game` 이 여는 것). 그 뒤 사용자 PC 에서 그 파일만 골라 zip 으로 묶는 단계를 둔다(로컬 컴퓨터 연결 · 스크립트).
- 리메이크 저장소 자체의 자료(`assets/` — 원작자가 만든 그림 등)는 APK 에 넣어도 되는지 출처를 확인한 뒤 넣는다.
- 대항해시대 경험: 큰 자료를 APK 에 넣을 때는 CI 가 받아 싣고(저장소에 커밋하지 않음), 처음 켤 때 앱 폴더로 꺼낸다(`AppContext` 기준 폴더를 그 자리로 거는 방법 — cds-remake `CostaDelSol.Android/Game/GameData.cs`).

## 5. 진행 순서

1. **정찰**: 저장소 구조 · 기술 · 원본 자료 읽는 길 · 윈도우 전용 지점 목록. (§0 이 출발점)
2. **iOS 앱 방식 분석**(공개 자료 범위 안에서).
3. **포팅 경로 결정 → 사용자에게 쉬운 말로 보고 → 승인 후 진행.** 이 게임은 두 길이 있다:
   - **(가) 소스 링크 포팅**(대항해시대와 같은 길, 스킬 `wpf-android-port` · `windows-game-to-android`): 원본 소스를 링크해 APK 를 굽는다. 원본이 고쳐지면 병합 → 다시 굽기. 이 게임은 그리기가 `uint[]` 화면이라 GL 텍스처 하나로 띄우면 되고 갈아 끼울 곳이 적어 유리하다.
   - **(나) 런처 + 실행 중 패치**(iOS 앱과 같은 계열, 스킬 `android-runtime-patch-port`): 사용자가 설치한 리메이크 dll 을 폰에서 읽어 윈도우 API 를 고쳐 돌린다. 원작자 업데이트를 APK 재빌드 없이 따라갈 수 있지만 만들기 · 고치기가 훨씬 어렵다.
   - 정찰 결과를 보면 (가)가 무난하다. 단, 최종 선택은 사용자가 한다.
4. **골격 + CI 를 맨 먼저**: 화면 하나 띄우는 APK 를 GitHub Actions 로 굽는다(ubuntu, .NET for Android). 브랜치 푸시마다 아티팩트, `android-v*` 태그에 릴리즈.
5. **갈아 끼우기**: 그리기(`_fb` → GLES 텍스처 / `HiCanvas` 층), 소리(waveOut → AudioTrack), 입력(키보드 · 마우스 → 터치 · 게임패드 · 화면 가상패드, 원본 단축키를 그대로 살리는 에뮬레이터식 바인딩), 창(WinForms 대화창 몇 개 → 같은 이름의 대용품), 파일 자리(`%APPDATA%` → 앱 폴더).
6. **헤드리스 시험기**: 같은 소스를 리눅스 콘솔로 컴파일해 처음 화면 → 전투 → 저장 까지 자동으로 돌리고 화면을 PNG 로 찍는다(cds-remake `devtools/sim`). 이 게임은 원작자의 화면 밖 시험 틀(`GameWindow.TestRun.cs`)이 있는지 먼저 본다.
7. **검수 2단계**(§6-6) → 고치기 → 릴리즈.
8. **원본 자료 추출 zip 작업**(§4).

## 6. 소통 · 작업 원칙 (대항해시대에서 굳어진 것)

1. **항상 한국어, 쉬운 말.** 사용자는 개발자가 아니고 영어를 못 한다. 전문 용어는 풀어 쓴다. 짧은 진행 알림도 한국어.
2. **분석 · 계획 요청은 고치라는 뜻이 아니다.** 큰 결정(구조 변경 · 되돌리기 어려운 일)은 먼저 묻는다. 정한 것은 다시 묻지 않는다.
3. **원본에 없는 UI · 글을 지어내지 않는다.** 원본(PC 판) 화면 코드 · 글 · 모양을 그대로 돌린다. 화면을 안드로이드용으로 다시 짓는 길은 대항해시대에서 갈아엎었다.
4. **사용자가 뺀 기능은 넣지 않는다.** 시작할 때 "뺄 후보" 표를 보여 주고 정한다 — 이 게임 후보: 자동 업데이트(Velopack) · 버그 리포트/통계 전송 · 편집기(Editor) · 고해상도 배경 AI(ONNX DirectML) · PC 파일 고르기 창 · 원작자 릴리즈에서 자료 내려받기(§7).
5. **단계마다 커밋 · 푸시.** 커밋 메시지 끝에 세션이 알려 주는 attribution 줄을 붙이고, 커밋 · 코드에 모델 이름을 적지 않는다.
6. **검수는 둘 다 해야 끝난다.**
   - 가검수(돌려서 터지는지): 전투 · 대본 · 저장 왕복 · 긴 진행을 시험기로 끝까지.
   - 진검수(PC 판과 맞대어 조용히 빠진 것): 링크 안 된 파일 · 정적 훅 대입 · 갈라 만든 파일의 함수 · 빈 대용 함수 중 게임이 부르는 것 · 설정이 실제로 읽히는지 (`wpf-android-port/scripts/gap_audit.py`).
   - 오류 0 인데 기능이 통째로 빠져 있던 일이 있었다 — 가검수만으로 끝내지 않는다.
7. **APK 를 줄 때마다 보고에 3가지**: ① APK 링크 `https://github.com/<소유자>/<저장소>/actions/runs/<run>/artifacts/<id>` ② 릴리즈 방법(releases/new → 태그 `android-vX.Y.Z` → Target 작업 브랜치 → zip 풀어 APK 끌어 놓기 → Publish) ③ 붙여 넣을 릴리즈 노트(코드 블록). 그리고 "직접 확인할 것"(시험기로 못 본 것) 목록.
8. **기기에서 확인 못 한 것은 확인 못 했다고 말한다.** 사용자 화면(스크린샷)이 오면 그것으로 고친다. 내가 잘못 안내했으면 바로 인정하고 바로잡는다.
9. **대화가 길어지면 한도가 빨리 닳는다**: 큰 파일은 필요한 부분만 읽고, 기다릴 때 상태 확인을 자주 하지 않는다(백그라운드로 한 번 기다린다). 방을 옮길 때는 **인계 노트**(지금 상태 · 결정 · 도구 · 검수 결과 · 함정)를 저장소 `docs/` 에 남긴다.
10. **CI 가 실패하면 로그부터 본다.** GitHub 쪽 일시 장애(릴리즈 내려받기 504 등)일 수 있다 — 그때는 사용자에게 그렇다고 말하고, 브랜치 빌드 아티팩트를 손으로 릴리즈에 붙이는 방법도 알려 준다.

## 7. 시작 전에 사용자에게 물을 것

1. 포팅 경로 (가) / (나) — §5-3 정찰 결과를 보고.
2. 뺄 기능 — §6-4 후보 표.
3. 파트1 · 파트2 둘 다인지, 하나부터인지.
4. 원작자 GitHub 릴리즈에서 받는 꾸러미(`AssetDownload`)를 안드로이드에서도 받게 할지(인터넷 필요), 아니면 사용자 PC 에서 만든 zip 에 함께 넣을지.
5. 대상 기기 · 화면 비율(폰 / 레트로이드 등, 4:3 · 16:9), 게임패드 유무.
6. 작업 브랜치 이름 · 앱 버전 · 릴리즈 태그 이름.

## 9. 대항해시대에서 배운 함정 (이 게임에도 미리 적용)

- **원본 코드를 다시 짜지 말 것** — 링크하고, 모자란 것만 흉내 낸다. 처음에 UI 를 다시 짓다가 갈아엎었다.
- **스레드**: PC 판의 "창을 띄우고 닫힐 때까지 기다리는" 코드(`ShowDialog` 류)는 게임 전용 스레드 + 메시지 펌프로 살려 원본을 안 고친다.
- **정적 훅**: 원본이 시작 코드(PC 전용 파일)에서 정적 속성 · 이벤트를 걸어 두는 곳이 있다. 그 파일을 안 쓰면 기능이 조용히 빠진다(대항해시대: 미궁 퍼즐 통째 누락). 진검수에서 "PC 에서는 대입하는데 안드로이드는 안 하는 것"을 꼭 본다.
- **흉내 낸 속성 세터는 같은 값이면 아무것도 안 해야** 한다 — 아니면 다시 배치가 끝없이 돌아 렉이 난다.
- 큰 창이 화면보다 크면 통째로 줄어 글자가 작아진다 — 안드로이드에서는 그 창만 `#if ANDROID` 로 판에 맞춘다.
- 메뉴 · 창이 떠 있는 동안 게임 시간(배 · 말 · 유닛)이 흐르지 않게 한다. 가상 패드는 메뉴 중 결정 · 취소만 남기는 것이 편했다(사용자 요청).
- 시작 영상이 실제 버튼으로만 넘어가 화면 패드 · 터치로 못 넘기던 일 — 모든 입력 길(실제 패드 · 화면 패드 · 가상 키보드 · 터치)을 같은 곳으로 모은다.
- 파일 BOM(첫 3바이트) 유무를 바꾸지 않는다. 원본 공용 파일을 고칠 때 diff 가 지저분해진다.
- 시험기 · 실행 중인 dll 을 덮어 빌드하지 않는다(출력 폴더를 번갈아). 병렬 실행은 코어 수만큼만.
- 시험기가 "버튼을 못 눌러" 멈추는 것은 게임 버그가 아닐 수 있다 — 0.9.6 코드로 같은 시험을 돌려 비교해 가린다.
